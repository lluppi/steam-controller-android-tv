# P1 — uhid spike on the Shield: **GO**

Run 2026-09-20 on the Shield TV (`$SHIELD`, see the private notes for the address).
No root. `uid=2000(shell)`, SELinux `Enforcing`.

## Why this mattered

The whole fork rests on one assumption the notes flagged as **"assumed — spike this
first"**: that a uhid device surfaces on this build as a real `InputDevice` with a
gamepad source class. It does. Both GO criteria are met.

`/dev/uinput` is `system:bluetooth` and the shell has no `bluetooth` group — confirmed
unreachable, matching the notes. `/dev/uhid` is group `uhid`, which the shell **is** in.

Two useful bonus facts:

- **`/system/bin/hid` exists** — AOSP's `hid` tool, so the spike needed zero compilation
  (see `spike/README.md`; the invocation is `hid <file>`, and a file without a trailing
  long `delay` exits immediately and destroys the device).
- **`/sys/bus/hid/drivers/sony` is present**, along with `microsoft` and `hid-generic`.
  That keeps P6 (rumble via DualShock 4 emulation / `hid-sony`) on the table.
- The Shield's **own remote is already a uhid device** on this build:
  `/sys/devices/virtual/misc/uhid/0005:0955:7217.0001/input/input2` (bus `0005` =
  BUS_BLUETOOTH, VID `0955` = NVIDIA) with `event2` + `hidraw0`. Independent,
  pre-existing evidence that this kernel's uhid path produces working input devices.

## Result — gamepad

```text
I NvControllers: Controller "Steam Controller (uhid spike)" detected!
I NvControllers: Controller "Steam Controller (uhid spike)" loaded (id=10)
D EventHub: No input device configuration file found for device 'Steam Controller (uhid spike)'.
I EventHub: New device: id=11, fd=196, path='/dev/input/event7',
            name='Steam Controller (uhid spike)', classes=0x80000141, configuration='',
            keyLayout='/system/usr/keylayout/Vendor_045e_Product_028e.kl',
            keyCharacterMap='/system/usr/keychars/Generic.kcm', builtinKeyboard=false,
I InputReader: Device added: id=11, name='Steam Controller (uhid spike)', sources=0x01000511
```

`sources=0x01000511` decodes as `SOURCE_KEYBOARD (0x101) | SOURCE_GAMEPAD (0x401) |
SOURCE_JOYSTICK (0x01000000)`.

**Android matched the real Xbox 360 keylayout** (`Vendor_045e_Product_028e.kl`) from the
VID/PID the descriptor advertises — i.e. declaring `bus = BUS_USB` with `045e:028e` still
picks up the keylayout, which is what the uinput backend relied on too. So the two backends
are interchangeable for Android's keylayouts *and* for RetroArch autoconfig, which keys on
the same name/vendor/product.

Capabilities, from `getevent -p`:

```text
add device 1: /dev/input/event5
  name:     "Steam Controller (uhid spike)"
  events:
    KEY (0001): 0130 0131 0132 0133 0134 0135 0136 0137
                0138 0139 013a 013b 013c 013d 013e
    ABS (0003): 0000  : value 0, min -32768, max 32767, fuzz 255, flat 4095
                0001  : value 0, min -32768, max 32767, fuzz 255, flat 4095
                0002  : value 0, min 0, max 255, fuzz 0, flat 15
                0003  : value 0, min -32768, max 32767, fuzz 255, flat 4095
                0004  : value 0, min -32768, max 32767, fuzz 255, flat 4095
                0005  : value 0, min 0, max 255, fuzz 0, flat 15
                0010  : value 0, min -1, max 1, fuzz 0, flat 0
                0011  : value 0, min -1, max 1, fuzz 0, flat 0
    MSC (0004): 0004
```

That is an exact capability match for the uinput backend's declarations: `ABS_X/Y/RX/RY`
int16, `ABS_Z/RZ` (triggers) 0-255, `ABS_HAT0X/Y` -1..1, and `BTN_A..BTN_THUMBR`.

Note on `0132` (`BTN_C`) and `0135` (`BTN_Z`) appearing in the KEY list: this is **expected
and harmless**, and the plan's earlier "fail condition" wording was too strict. `hid-input`
maps gamepad button N to `BTN_GAMEPAD + N - 1`, so a 15-button declaration yields the
*contiguous* range `0x130..0x13e`. Indexes 3, 6, 9 and 10 exist in the bitmap but are never
set by the packer (`XBOX_BUTTONS` in `hid_common.h` skips them), so `BTN_C`/`BTN_Z` are
declared-but-never-emitted — the same trick the real Xbox One S Bluetooth descriptor uses.
The contiguity of that range is itself the proof that the table's indexes line up.

## Result — mouse

```text
I EventHub: New device: id=12, fd=211, path='/dev/input/event8',
            name='Steam Controller Mouse (uhid spike)', classes=0x80000008,
            configuration='', keyLayout='', keyCharacterMap='', builtinKeyboard=false,
I InputReader: Device added: id=12, name='Steam Controller Mouse (uhid spike)', sources=0x00002002
```

`sources=0x00002002` = `SOURCE_MOUSE (0x2000) | SOURCE_CLASS_POINTER (0x02)`.

This is the property that kills `inject` mode: a **real mouse device**, so the cursor is
driven system-wide in any app — launcher, browser, video apps — not just whichever window
holds focus.

## Verdict

**GO.** The architectural bet is won: on this device `/dev/uhid` delivers a genuine
gamepad (`SOURCE_GAMEPAD`) *and* a genuine system mouse (`SOURCE_MOUSE`) at the same time,
with no root, no SELinux denial, no kernel oops and no reboot. Every "Phase 2+" step in
PLAN.md is unblocked.

## Not verified (deliberately honest)

- **Event-level flow.** The devices are created and classified correctly, but no capture of
  the *emitted* events (a physical button press producing the matching `BTN_*`) was
  obtained — see the link instability below. The report packing is unproven in motion.
- **The cursor visually moving.** Only the device class is proven; a human has to watch the
  TV. Do this in P3.S6.
- **The app.** Nothing of the fork's own code has run on the device yet. P3.S6 (install,
  connect, play) is the real acceptance test.

## New field data — the adb link drops when `hid` runs

Not in the notes, and it cost several attempts:

- Running AOSP's `hid` tool for more than a few seconds **drops the adb connection**
  (`error: closed` / `device offline`), reproducibly, four times out of four. A ~5s run is
  fine; a longer one is not.
- It is **not** a crash: `uptime` advanced monotonically across every occurrence (1330s →
  1501s), and there is no oops, panic or `avc: denied` in `logcat -b all`. The device keeps
  working; only the adb link goes.
- The on-device work still completes — the gamepad and mouse both registered during runs
  whose adb sessions had already dropped.
- Consequences for the next person: `nohup ... &` does **not** reliably keep a capture
  process alive across such a drop, so a background `getevent`/`logcat` capture started
  from one adb session can be lost when the link goes. Budget for retries, and prefer
  reading the persistent `logcat` buffer after the fact over streaming a live capture.
- Why `hid` specifically: it is a Java/`app_process` tool rather than a native binary.
  `getevent` (native) detaches and survives, as the notes describe; the `hid` process does
  not survive backgrounding at all (it dies with the session, writing nothing).
